# 코드 검수 프로토콜

AI 리뷰는 세 번을 돌려도 지적 목록이 줄지 않는다. 지적은 끝없이 나오지만 고칠 것은 얼마
없다. 그래서 리뷰를 그대로 받지 않고 **리뷰 자체를 검증 대상**으로 삼는다.

이 문서는 위임 프롬프트에 **그대로 붙여 넣는** 용도다. 링크만 걸어두면 읽히지 않는다.
읽히지 않은 규칙은 없는 규칙이다.

---

## 구조

두 단계다. 수집하고, 반박한다.

```
        ┌─ 축 1 에이전트 ─┐
        ├─ 축 2 에이전트 ─┤
변경본 ─┼─ ...           ─┼─→ 지적 목록 ─→ 지적마다 반박 에이전트 1개 ─→ 생존한 지적만 수정
        └─ 축 N 에이전트 ─┘
```

### 1단계 — 수집

검수 축을 **4~12개**로 쪼갠다. 축마다 에이전트 하나를 동시에 붙인다.
축은 작업 성격에 따라 고르되, 이 프로젝트의 기본 축은 아래와 같다.

| 축 | 본다 |
|---|---|
| 정확성 | 로직 오류, 경계 조건, 단위 혼동 (px/mm/rad) |
| 좌표계 | `X_w / X_c / (x,y) / (u,v)` 혼용, 왜곡 적용 방향 |
| 조용한 실패 | 예외 삼키기, 기본값으로 넘어가기, 검증 없는 가정 |
| 재현성 | 시드, 정렬 순서, 파일 순서 의존 |
| 규칙 준수 | `CLAUDE.md`·`README.md`의 확정 사항과 충돌 |
| 테스트 | 빠진 케이스, 실제로 검증하지 않는 테스트 |
| 데이터 무결성 | 세션 메타데이터 누락, 덮어쓰기 위험 |
| 의존성 | 승인 없는 패키지, 버전 고정 없음 |

**수집 에이전트가 올리면 안 되는 것:**

- 컴파일러·린터·테스트가 이미 잡은 것
- **재현 시나리오를 대지 못하는 것.** "이럴 수도 있다"는 지적이 아니다
- 스타일 취향. 프로젝트 규칙에 명시된 것만 규칙이다

지적 하나의 형식:

```
[축] 한 줄 요약
위치: 파일:줄
재현: 이 입력을 넣으면 이 결과가 나온다
영향: 무엇이 틀어지는가
```

### 2단계 — 반박

지적마다 **별도 에이전트**를 붙여 반박시킨다. 수집한 에이전트가 아니어야 한다.

**반박 에이전트의 기본 판정은 기각이다.** 지적이 살아남으려면 반박 에이전트가
재현을 직접 확인해야 한다. 확신이 없으면 기각을 유지한다.

판정은 셋 중 하나:

- **기각** — 재현 안 됨, 이미 처리됨, 규칙 위반 아님, 영향 없음
- **채택** — 재현 확인, 수정 필요
- **기존 결함** — 맞는 지적이지만 이번 변경이 만든 것이 아님. 별도 이슈로 기록, 이번 수정 범위 밖

### 3단계 — 수정

채택된 것만 고친다. 기존 결함은 `result.md`의 이슈 목록에 적고 넘어간다.

---

## 전제 검증

리뷰가 **전제한 주장**부터 의심한다. 지적 8건이 같은 전제 위에 서 있으면, 8건을 반박하는
것보다 전제를 6개 축으로 쪼개 반증하는 편이 빠르다. 전제가 깨지면 8건이 함께 사라진다.

되돌리기 어려운 변경(배포 설정, 데이터 스키마, 세션 포맷) 앞에서는 **영향 범위 조사가
먼저**다. 조사 결과 "코드를 바꾸지 않는다"가 결론일 수 있고, 그것도 성과다. 가장 많이
투입한 작업의 산출물이 0줄인 경우가 있다.

## 위임 규칙

멀티 저장소·멀티 모듈 작업에서 에이전트가 각 위치의 검증 규칙을 읽지 않고 지나간 실패가
있었다. 서식 불일치와 오류 코드 미등재가 남았다.

그래서:

1. 적용할 규칙을 **위임 프롬프트 본문에 적는다.** `CLAUDE.md` 참조로 끝내지 않는다
2. 에이전트가 끝나면 **결과를 다시 감사한다.** 규칙 준수 축을 반드시 포함
3. 한 위임에 한 모듈. 여러 곳을 동시에 맡기지 않는다

## 반박 에이전트 프롬프트 템플릿

```
다음 지적을 반박하라. 기본 판정은 기각이다.

지적:
<지적 전문>

대상 코드:
<파일 또는 diff>

절차:
1. 지적이 말하는 재현 시나리오를 실제로 실행하거나 추적한다
2. 재현되지 않으면 기각. 이유를 한 줄로
3. 재현되면 이번 변경이 원인인지 확인한다. 아니면 "기존 결함"
4. 재현되고 이번 변경이 원인이면 채택. 최소 수정안을 한 줄로

확신이 없으면 기각을 유지한다.
출력: 판정 / 이유 / (채택 시) 수정안
```

## 수집 에이전트 프롬프트 템플릿

```
축: <축 이름>
이 축에서만 본다. 다른 축의 문제는 무시한다.

대상:
<파일 또는 diff>

프로젝트 규칙 (그대로 적용):
<README 확정 사항·원칙 절 붙여넣기>

올리지 않는 것:
- 린터·테스트가 이미 잡은 것
- 재현 시나리오를 댈 수 없는 것
- 규칙에 없는 스타일 취향

형식:
[축] 요약 / 위치 / 재현 / 영향
```

## 기록

검수 한 번마다 `result.md`에 한 줄:

```
YYYY-MM-DD 검수 | 대상 | 수집 N축 M건 | 채택 a / 기각 b / 기존결함 c | 수정 L줄
```

1년치 누적으로 어떤 축이 실제 결함을 잡고 어떤 축이 소음만 내는지 보인다.
소음만 내는 축은 뺀다.
