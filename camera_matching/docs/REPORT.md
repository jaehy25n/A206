# S10 ↔ LUAZ 카메라 매칭 — 진행 보고

2026-09-21 · 2회차

---

## 1. 무엇을 하려는 일인가

**학습은 Galaxy S10 으로 모은 영상으로 하고, 실제 운용은 LUAZ WC1080 웹캠으로 한다.**
두 카메라는 렌즈가 달라 같은 물체가 다른 크기·다른 위치·다른 왜곡으로 찍힌다.
그대로 두면 S10 으로 배운 모델이 LUAZ 영상에서 어긋난다.

그래서 **S10 영상을 LUAZ 규격으로 옮기는 변환**을 만드는 것이 이번 회차의 목표다.

이번 회차 범위는 **기하(geometry)** 뿐이다. 밝기·색·선명도 매칭은 다음 회차다.

---

## 2. 결과 — 지금 쓸 수 있는 것

### 변환 프로그램이 동작한다

카메라 영상을 넣으면 공통 규격으로 바꿔 돌려준다.

```python
from camcal.stream import FrameRemapper

remapper = FrameRemapper.from_files("results/s10_intrinsics.json")
out = remapper.apply(frame)     # 이것이 전부
```

| 항목 | 값 |
|---|---|
| 처리 속도 | **프레임당 3.65 ms** (1920×1080 기준, 274 fps 상당) |
| 실시간 여유 | 30 fps 예산 33 ms 의 **11%** 만 사용 |
| 검은 영역 | S10 1.23%, LUAZ 0% (`--crop` 으로 잘라낼 수 있음) |

속도는 문제가 되지 않는다. 맵을 한 번만 계산하고 이후에는 표만 찾는 구조다.

### 전체 도구

| 단계 | 도구 | 하는 일 |
|---|---|---|
| 1 | `capture_luaz.py` | LUAZ 체커보드 촬영 |
| 2 | `run_s10_server.py` | S10 을 노트북에서 원격 촬영 (HTTPS 웹앱) |
| 2 | `preflight_jitter.py`, `path_check.py` | 촬영 전 점검 (손떨림 보정, 촬영 경로) |
| 3 | `run_calibrate.py` | 촬영본 → 카메라 파라미터 + 품질 리포트 |
| 4 | `run_fov_compare.py` | 두 카메라 비교 → 공통 규격 결정 지표 |
| 5 | `run_remap.py`, `run_video_remap.py` | 실제 변환 (파일 / 영상) |

테스트 **324개**, 전부 카메라 없이 돈다.

## 3. 설계 결정 — 공통 규격을 무엇으로 할 것인가

두 안이 있었다.

| | ② LUAZ 원본을 기준으로 | ③ 가상 카메라를 기준으로 |
|---|---|---|
| LUAZ 영상 | 건드리지 않음 | 매 프레임 변환 |
| S10 영상에 하는 일 | LUAZ 의 왜곡을 **입힌다** | 왜곡을 **제거한다** |
| 운용 시 부담 | 없음 | LUAZ 도 변환 |

**③ 을 골랐다.** 운용 부담이 있는데도 고른 이유는 **불확실성이 번지는 방향** 때문이다.

지금 왜곡 계수의 신뢰도가 낮다(5장). ② 는 그 값을 S10 영상에 **주입**하므로 값이
틀리면 오차가 더해진다. ③ 은 **제거**하는 방향이라 값이 틀려도 덜 펴질 뿐 오차가
더해지지는 않는다. 같은 불확실성에서 손해가 작은 쪽을 택했다.

부수적으로, 나중에 재촬영해 값이 바뀌어도 ③ 은 기준 규격만 고정해두면 바뀐 쪽만
다시 돌리면 된다. ② 는 S10 변환본을 전부 다시 만들어야 한다.

결정은 `results/target_space.json` 파일 하나에 기록되어 있고, 모든 변환이 그 파일을
읽는다. 코드가 임의로 고르지 못하게 막아두었다.

## 4. 검증한 것

숫자 하나(RMS)로 판단하지 않고 네 가지를 함께 본다. 모든 실행이 리포트를 남긴다.

| 확인 항목 | 왜 필요한가 |
|---|---|
| 오차의 공간 분포 | 전체 평균이 낮아도 화면 한쪽만 틀릴 수 있다 |
| 잔차의 방향성 | 가장자리에서 한 방향으로 쏠리면 왜곡 모델이 부족한 것 |
| 파라미터 안정성 | 사진 일부만 바꿔도 값이 흔들리면 데이터가 부족한 것 |
| 홀드아웃 검증 | 추정에 쓰지 않은 사진으로 따로 확인 |

변환 정확도는 **체커보드 직선성**으로도 확인했다. 왜곡 보정 후 격자 한 줄이 실제로
더 곧아지는지를 쟀고, 보정을 하지 않은 경우보다 **평균 14% 개선**되었다.
보정 방향이 맞다는 뜻이다.

## 5. 한계 — 지금 값을 얼마나 믿을 수 있나

**결론부터: 지금 값은 기준 미달이다. 알고 쓰는 중이다.**

| 항목 | 목표 | 현재 | |
|---|---|---|---|
| 재투영 오차 | < 0.3 px | 0.39 ~ 0.47 px | 미달 |
| 초점거리 안정성 | < 1% | 3.5% | 미달 |
| S10 초점거리 | — | 촬영 회차 간 **16% 불일치** | 미해결 |

### 원인은 촬영 조건이다

촬영 사진을 보면 **체커보드를 손으로 들고 찍었고**, 보드가 화면 가장자리까지 닿지
않았다. 두 가지가 겹쳐 다음을 만든다.

- 손으로 들면 미세한 기울어짐이 사진마다 섞인다 → 오차가 전반적으로 올라간다
- 보드가 가장자리에 안 닿으면 **왜곡 계수가 제대로 풀리지 않는다**
  (실제로 두 카메라 모두 광각 렌즈에서는 나오지 않는 부호의 값이 나왔다)

### 재촬영이 필요하지만 이번 회차에는 불가능했다

일정상 재촬영을 할 수 없어, **남은 데이터에서 더 뽑을 수 있는지**를 먼저 확인했다.

- 왜곡 모델을 단순하게 줄여보았다 → 홀드아웃 오차가 **오히려 나빠졌다**
- 두 촬영 회차 중 어느 쪽을 쓸지 교차 검증했다 → 장수가 적은 쪽(23장)이
  **더 잘 일반화**했다 (많은 쪽 40장은 자기 데이터에만 잘 맞았다)

즉 **현재 채택값이 이 데이터에서 뽑을 수 있는 최선**이다. 더 개선하려면 재촬영이
유일한 방법이다.

### 이것이 실제로 무엇을 뜻하나

초점거리가 16% 틀리면, 1 m 앞의 30 cm 물체가 582 px 대신 675 px 로 보인다.
모델이 거리나 크기를 판단한다면 **그만큼 한 방향으로 치우친 오차**를 갖는다.
무작위 오차가 아니라 계통 오차라 더 나쁘다.

다만 이것은 **최악의 경우**다. 16% 는 두 회차의 차이일 뿐 어느 쪽이 맞는지는
모르며, 실제 오차는 그보다 작을 수 있다.

## 6. 다음에 할 일

### 재촬영 (가장 중요)

다음 세 가지만 지키면 위 문제가 대부분 해결된다.

1. **보드를 고정한다** — 거치대나 벽에. 손으로 들지 않는다
2. **화면 가장자리까지 채운다** — 보드가 화면 밖으로 반쯤 나갈 만큼 밀어서도 찍는다
3. **기울기를 크게 준다** — 좌우상하 25~50도

### 초점거리 검증 (1분, 재촬영 없이도 가능)

자로 카메라-보드 거리를 한 번 재면 초점거리가 맞는지 바로 확인된다.
16% 불일치 문제를 즉시 판정할 수 있는 유일한 방법이다.

```
python src/check_align.py --camera s10 --distance-mm 400 사진.png
```
