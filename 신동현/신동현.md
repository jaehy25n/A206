# 오늘 공부한 내용

로봇 데이터 수집 플랫폼 프로젝트에서 스마트폰을 카메라와 IMU 센서가 같이 들어있는 데이터 수집 장치로 활용하려고 한다.

스마트폰으로 작업 영상을 촬영하면서 카메라의 움직임이나 궤적까지 같이 얻고 싶어서, 이후에는 스마트폰 카메라와 IMU 데이터를 기반으로 ORB-SLAM 쪽을 구현하고 최적화해보려고 한다.

바로 ORB-SLAM 코드를 가져다 쓰기보다는 영상이 실제로 어떻게 처리되고, 픽셀 접근이나 convolution 같은 기본 연산이 어느 정도 비용을 가지는지 먼저 이해해보고 싶어서 Canny Edge Detection을 직접 구현하고 최적화하는 공부를 진행하고 있다.

오늘은 기존에 구현해둔 Canny 코드를 계속 최적화했다.

먼저 `Mat::at()`으로 픽셀에 접근하던 부분들을 `ptr()`을 이용한 Row Pointer 방식으로 바꿨다.

Grayscale, Gaussian, Sobel뿐만 아니라 Gradient, NMS, Threshold, Cleanup까지 Pointer 접근으로 변경했다. 단순히 `at()`을 없애는 것 자체가 목적이라기보다는, 영상처럼 한 Row를 계속 순차적으로 읽는 작업에서 매 픽셀마다 Mat을 통해 접근하는 것보다 Row 시작 주소를 한 번 받아서 접근하는 게 어떤 차이가 있는지 확인해보는 식으로 진행했다.

생각보다 차이가 꽤 컸다.

특히 NMS는 평균 약 `15.65 ms → 3.18 ms`, Threshold는 `7.83 ms → 3.21 ms`, Cleanup은 `4.60 ms → 0.37 ms` 정도까지 줄었다.

반대로 Gradient는 Pointer로 바꿔도 여전히 약 `10 ms` 정도가 걸렸다.

Gradient에서는 `sqrt()`와 `atan2()`를 픽셀마다 계산하고 있는데, 이걸 보면서 모든 느린 코드가 메모리 접근 문제인 것은 아니고 실제 계산 자체가 병목이 되는 구간도 있다는 걸 좀 체감했다.

그리고 의문의 고수의 블로그에서 결국 이미지 처리는 대규모 순차처리이기 때문에
for문에 들어가는 변수 개수나 증가 연산 등을 하나로 묶어서 처리하는 최적화가 효과적
이라고 해서 적용해봤지만 효과는 미미했다. 
아마도 Task의 성격이 달라서이기 때문인 것 같다.

결국 중요한 건 문법적으로 Pointer를 쓰느냐가 아니라 현재 병목이 어디에 있느냐인 것 같다.

Hysteresis 쪽은 조금 다르게 봤다.

Hysteresis는 Queue를 사용하는 BFS 구조라서 한 Row를 순서대로 도는 게 아니라 Strong Edge 주변 8개 픽셀을 계속 불규칙하게 찾아간다. 그래서 이 부분은 굳이 `at()`을 전부 Pointer로 바꾸지 않고 그대로 두었다. 

예전에 Hysteresis가 전체 Frame을 계속 다시 Scan하는 방식이어서 200~300 ms 이상 걸렸는데, BFS로 바꾼 뒤 이미 5 ms 전후까지 줄어든 상태라 여기서 Pointer를 조금 더 만지는 것보다 다른 병목을 보는 게 낫다고 생각했다.

Gaussian은 3×3 kernel을 그대로 계산하던 방식에서 separable convolution으로도 변경했다.

`[1 2 1]` Horizontal 연산을 한 번 하고, 다시 Vertical 연산을 하는 식으로 바꾸면서 Gaussian은 현재 평균 `0.85 ms` 정도까지 내려왔다.

오늘 최종 Benchmark는 고정된 640×480 영상 300 Frame을 미리 메모리에 올리고, Warm-up 1회 후 5번 반복해서 총 1500 Frame을 측정했다.

결과는 다음과 같았다.

```text
Gray         2.99 ms
Gaussian     0.85 ms
Sobel        7.02 ms
Gradient    10.30 ms
NMS          3.18 ms
Threshold    3.21 ms
Hysteresis   4.22 ms
Cleanup      0.37 ms

TOTAL       32.15 ms
Mean FPS    31.10 FPS
```

평균 기준으로는 처음으로 30 FPS 기준인 `33.33 ms/frame` 안에 들어왔다.

다만 P95는 `37.44 ms`라서 아직 안정적으로 모든 Frame을 30 FPS Budget 안에서 처리한다고 보기는 어렵다.

오늘 하면서 제일 많이 느낀 건 최적화할 때 무조건 "Pointer가 빠르다", "멀티스레드하면 빨라진다"처럼 하나의 방법만 보는 게 아니라, Profile을 보고 그 Stage가 왜 느린지를 먼저 봐야 한다는 점이었다.

Hysteresis는 알고리즘 구조 자체가 문제였고, NMS나 Cleanup은 메모리 접근 방식의 영향이 컸고, 지금 Gradient는 `sqrt()`와 `atan2()` 같은 연산 자체가 다음 병목으로 보인다.

다음에는 Gradient에서 정확한 각도를 `atan2()`로 전부 구한 뒤 다시 0°, 45°, 90°, 135°로 나누는 방식을 없애고, `Gx`, `Gy`에서 바로 방향을 분류하는 방식을 먼저 해볼 생각이다.

그다음 FAST, BRIEF, ORB 쪽으로 넘어가려고 한다.

결국 지금 하는 Canny 구현/최적화는 Canny 자체가 최종 목표라기보다는, 이후 스마트폰 영상에서 Feature를 뽑고 Matching하고 카메라 움직임을 추정해서 ORB-SLAM 기반 궤적을 얻는 과정으로 넘어가기 전에 영상 처리 코드와 성능 병목을 직접 경험해보기 위한 밑바탕 공부라고 보면 될 것 같다.
