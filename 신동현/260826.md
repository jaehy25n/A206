1. type 실수 -> unpreditacble latency?
처음에는, Type 실수를 의심했다. 기존 angle 값을 32F로 받고 있었는데, 바꾼 후에는 각도 범위만 값을 가지면 되서 uchar로 바꿔야 했다.

실제 코드를 확인해 본 결과, Mat의 실제 저장 타입과 ptr 접근 타입은 일치하고 있었다.

오히려 기존 float angle map과 비교하면 4 byte/pixel → 1 byte/pixel 로 저장량이 줄었으므로, 자료형 변경 자체가 4~5ms의 추가 지연을 발생시켰다고 보기는 어렵다.

따라서 Type 문제는 일단 제외했다.

2. Branch 자체가 정말 비싼건가?
명확하게 보이는 건, 세타 하드코딩에 비해서 Branch가 추가되었다는 점 그래서 30분 넘게 코드를 보고 생각하면서 이 Branch가 왜 이렇게 비쌀까를 생각해 봤다.

솔직히 도저히 스스로 정답을 도출해 내기 어려웠다. 그나마 보이는 것은, 앞서 찾았던 이유인 NMS에서의 Branch를 Gradient로 끌어왔다는 점 근데 NMS에서도 거의 동일한 Branch를 실행했었지만, Branch 제거 후

기존 NMS : ~3.18 ms direct-dir NMS : ~2.82 ms ↓ -0.36 ms

밖에 지연 이득이 없었다.

즉, Gradient에 추가된 약 4.97ms를 단순히 NMS에서 옮겨온 방향 분류 branch의 실행 비용만으로 설명하기는 어렵다. 라는 단서는 얻을 수 있었다.

그리고 NMS와 수정 전 Gradient, 수정 후 Gradient를 비교해 보면서 몇 가지 가설을 세워봤다.

NMS에서는 방향 분류 쪽에서 약 0.36ms 정도 차이가 났는데, 비슷한 역할의 작업을 Gradient 쪽으로 가져온 이후에는 비용이 훨씬 크게 증가했다.

Gradient 내부에서 의미 있는 비교는 theta hardcode vs direct quantization이라고 생각했다.

 라고 생각했다.

 NMS에서도 방향에 따른 branch는 이미 있었는데,
 direct-dir로 바꾼 뒤 얻은 이득은 약 0.36ms 정도였다.

 -> 그러면 branch prediction 하나만으로
 Gradient의 +4.97ms를 설명하는 건 좀 이상하다.
사실상 NMS의 Branch는 견고하다. 그저, 범위를 구하는 것을 옮겼을 뿐 살펴보면, NMS에서 branch 결과에 따라서 다른 메모리 주소에 접근을 한다 이러한 패턴은, 컴파일러 최적화기에 어려운 위에서 말한 noisy한 패턴으로 보인다. 그렇다면, 이런 가설은 어떨까? 기존 gradient는 충분히 컴파일러 최적화가 가능한 형태였는데 NMS에서 해당 부분을 가져오면서 최적화가 깨졌고 NMS는 해당 부분이 빠지더라도 여전히 noisy branch task이기 때문에 큰 영향이 없었다.

-> 이를 실험하기 위해서 Gradient로 옮긴 분류 부분을 다시 NMS로 옮겨보기로 했다

3. Direct Quantization을 다시 NMS로 옮겨봤다.
연산 자체가 비싼 것인지, Gradient loop 안에 들어갔을 때 유독 느려지는 것인지 확인하기 위해 direct quantization 코드를 그대로 NMS로 옮겨봤다.
