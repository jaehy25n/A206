# 02. 로봇 제어 아키텍처

## 0. 조직 원리

로봇 제어는 **중첩된 피드백 루프의 사슬**이다. 각 층은 위층보다 대략 10배 빠르고, 아래층이 이미 세상을 안전하게 만들어놨다고 믿는다.

> 정책 5–15 Hz → 궤적 제어기 100 Hz → 서보 PID ~1 kHz → PWM 수십 kHz

만드는 것은 결국 **"사람 없이, 모터당 1 ms에 포화된 정수 하나를 고르는 방안"** 이다.
구조가 존재하는 이유는 하나 — **위쪽의 느리고 경계 없고 틀릴 수도 있는 계산이 아래쪽에서 설정값 불연속을 만들지 못하게** 하려는 것.

그래서 실체는 **경계 규율**: 무엇이 / 어떤 단위로 / 어떤 주기로 넘어가는가, 그리고 위층이 멈추거나 거짓말할 때 아래층이 무엇을 하는가.
공정은 아키텍처를 따라간다 — **아래에서 위로, 싼 것에서 비싼 것으로**. 1층을 확인한 적이 없으면 3층의 고장은 1층의 고장과 구별이 안 된다.

## 1. 계층 스택

| 계층 | 주기 | 아래로 넘기는 것 | 실제 구현 | RT |
|---|---|---|---|---|
| 운영자 / 태스크 | 에피소드 | 목표 포즈, "정책 시작" 플래그 | 사람 + 래칭 버섯 e-stop | – |
| 계획 *(선택)* | 0.05–2 s, 최악 무한 | `FollowJointTrajectory` 목표, 0.1 s 간격 웨이포인트(rad) | MoveIt 2 `move_group`, OMPL RRTConnect, TOTG | ✗ |
| **학습 정책** | 5–15 Hz | `[H, action_dim]` — 절대 관절각(ALOHA/LeRobot) *또는* 상대 SE(3) EE 델타 + 절대 그리퍼 폭(UMI) | torch, 별도 프로세스/컨테이너 | ✗ |
| **속도 브리징 실행기** | 리플랜 4–10 Hz | `JointTrajectory`(positions rad, velocities rad/s, time_from_start) — **액션이 아니라 토픽** | 직접 만든 rclpy 노드 | soft |
| 궤적 제어기 | 100 Hz | 관절당 double 하나(rad), 직렬화 없이 공유 메모리로 | `JointTrajectoryController` | ✓ |
| controller_manager | 100 Hz (벤더 설정 확인) | `read() → update() → write()` 심장박동, 인터페이스 단일 점유 강제 | `ros2_control_node` (단일 프로세스) | ✓ |
| 하드웨어 인터페이스 | 매 사이클 | Sync Write 1회(4 B × 6) + 활성화 때 레지스터 일괄 주입 | `dynamixel_hardware_interface`, `is_async="true"` | soft |
| **전송: USB + 반이중 버스** | 왕복 2–4 ms | Protocol 2.0 패킷, 1 Mbps 8N1 | OpenRB-150 / U2D2 → `/dev/ttyACM0` | ✗ |
| 서보 프로파일 생성기 | 목표 쓸 때마다 재생성 | 사다리꼴 속도 프로파일 → PID | Drive Mode 4 (bit2 = **시간 기반**) | ✓ 펌웨어 |
| 서보 PID | ~1 kHz (추정, 비공개) | 부호 있는 PWM duty | P/I/D = 1000/0/1000 | ✓ |
| 커뮤테이션 | 수십 kHz | 모터 토크 | 각 서보 안의 Cortex-M + H-브리지 | ✓ HW |

### 이 표에서 읽어야 할 것

1. **선(wire)이 진짜 천장이다.** 버스 산술로는 read+write 한 사이클 1.78 ms(562 Hz)지만, USB Full-Speed가 1 ms 프레임으로 스케줄해서 실제 왕복 2–4 ms → **정직한 상한 200–300 Hz**. 다이어그램에 안 나오는데 지연 예산이 조용히 소모되는 곳. *(계산값, 이 장비에서 실측 필요)*
2. **서보 프로파일 생성기는 끌 수 없는 마지막 방어선.** 호스트에게 안 보이면서 명령 스트림을 조용히 필터링한다. 100 Hz로 쏴도 ~50 ms 프로파일을 통과하므로 **제어율을 올려서 덜컹거림을 고치려는 건 필터를 오버샘플링하는 것.** 손잡이는 Profile Velocity다.
3. **P=1000, I=0.** KPP = 1000/128 = 7.8125 PWM/pulse, PWM 포화 885 → **약 10° 추종 오차면 이미 전력 최대.** I=0이므로 중력 처짐 6.48 mm는 고장이 아니라 설정된 결과(일정 부하 → 일정 오프셋).
4. 벤더 JTC는 `command_interfaces: [position]`만 선언 → 메시지에 넣은 velocity는 스플라인 모양만 바꾸고 **하드웨어엔 도달하지 않았다.** (속도 피드포워드는 원래 없었다)

## 2. ROS 2 노드 그래프 (매니퓰레이터)

```
          rmw_zenohd  (tcp/7447)          ← ROS 노드가 아님. 이게 "그래프" 그 자체
                 │
   ┌─────────────┴──────────────┐
   │      ros2_control_node     │  ← /dev/ttyACM0을 소유하는 유일한 프로세스
   │   controller_manager       │
   │   DynamixelHardware        │
   │   joint_state_broadcaster ─┼──→ /joint_states
   │   arm_controller (JTC)   ←─┼─── /arm_controller/joint_trajectory
   └────────────────────────────┘
          │                    ↑
   robot_state_publisher       │
          │ → /tf, /tf_static  │
          ↓                    │
       rviz2            정책/chunk 실행기 (내 노드)
                               ↑
                        카메라 드라이버 → /camera1/image_raw
```

| 노드 | 역할 | pub / sub | 알아둘 것 |
|---|---|---|---|
| `rmw_zenohd` | Zenoh 라우터 | – | **ROS 노드가 아님**, `ros2 node list`에 안 보임. 없으면 노드들이 깨끗이 뜨고 로그 없이 서로 못 봄. `ss -ltnp \| grep 7447`이 ROS 디버깅보다 먼저 |
| `ros2_control_node` | 포트 소유 + controller_manager + HW 플러그인 + 제어기 전부 | `/controller_manager/*` 서비스 | 자체는 lifecycle 아니지만 내부 HW·제어기의 lifecycle을 몬다 |
| `joint_state_broadcaster` | 상태 인터페이스 → ROS 그래프 다리 | pub `/joint_states`, `/dynamic_joint_states` | **active가 아니면** `/joint_states` 없음 → `/tf` 빔 → RViz 회색 → MoveIt 거부 → 정책 노드는 **에러 없이 영원히 대기**. 원인 하나, 증상 넷 |
| `arm_controller` (JTC) | 궤적 보관 + 실시간 보간 | sub `/arm_controller/joint_trajectory`, action `follow_joint_trajectory` | 활성화가 곧 joint1..5 command 인터페이스 점유. velocity 없으면 **선형 보간**, 마지막 점 velocity≠0이면 **메시지 전체 거부** |
| `spawner` | load → configure → switch 후 종료 | – | **실패해도 exit** → launch `OnProcessExit`가 어느 쪽이든 발화, 죽은 팔 위에서 RViz가 뜬다. `ros2 control list_controllers`로 확인 |
| `robot_state_publisher` | URDF → KDL 트리, `/joint_states` → `/tf` | pub `/tf`, `/tf_static`(TRANSIENT_LOCAL), `/robot_description` | 두 번째 로봇은 namespace(토픽)와 frame_prefix(TF) **둘 다** 필요 |
| `move_group` | 계획 (컨트롤러의 액션 **클라이언트**) | `/planning_scene`, `/compute_ik` … | 벤더 AI 런치(`omx_f_follower_ai.launch.py`)에는 **아예 없음** — 정책이 곧 플래너, 런타임 충돌 검사 없음 |
| `rviz2` | 순수 소비자 | sub `/tf`, `/robot_description` | 관절 부호 오류를 몇 초에 잡는 유일한 도구 |
| 카메라 드라이버 | 프레임 + 내부 파라미터 | pub `image_raw`, `camera_info` | 이미지 토픽은 **BEST_EFFORT** → RELIABLE 구독자는 **조용히 영원히 연결 안 됨** |
| 정책 / chunk 실행기 | 상태 읽기 → 추론 → 디코드 → 궤적 publish | pub 궤적, sub `/joint_states`, 이미지 | 벤더는 `:144`에서 `/arm_controller/joint_trajectory` → `/leader/joint_trajectory` 리맵 — **정책이 리더 팔 자리를 차지**, 텔레오퍼레이션과 교체 가능 |
| rosbag2 | 녹화(비행기록 겸 데이터셋) | 지정 토픽 | 받은 것만 기록 — 부하 시 best-effort 이미지 조용히 누락 |

### 꼭 알아둘 메커니즘

- **topic vs service vs action**: 호밍은 **액션**(결과·피드백·선점 필요), 정책은 **토픽**(매 메시지가 핸드셰이크 없이 이전 것을 대체, 200 ms 뒤 취소할 결과 콜백은 무용)
- **TF**: "no transform from X to Y"는 TF 버그가 아닌 경우가 대부분. 순서: `/joint_states` 나오나 → 체인의 모든 관절 포함? → frame_prefix? → `/tf_static`을 VOLATILE로 늦게 구독? → 조회 시각이 10 s 버퍼 안? `ros2 run tf2_tools view_frames`
- **QoS**: offer가 request를 지배해야 연결. BEST_EFFORT pub + RELIABLE sub ✗, VOLATILE pub + TRANSIENT_LOCAL sub ✗. **불일치는 설계상 조용하다.** `ros2 topic info <t> --verbose`가 첫 가설
- **executor**: 기본 단일 스레드에서 콜백 안에서 서비스를 동기 호출하면 영원히 멈춘다. 100 Hz 타이머와 40 ms 이미지 전처리를 같은 executor에 두면 남는 만큼만 돈다 — **요청한 주기가 아니라 실측 주기를 믿어라**
- **디스커버리**: `ros2 node list`가 비면 코드 버그가 아니라 디스커버리. 라우터 떠 있나 / 두 셸의 `RMW_IMPLEMENTATION`, `ROS_DOMAIN_ID` 같나

## 3. 격리 — 도커가 하는 것과 못 하는 것

### 하는 것 (각 관행이 막는 실패)

| 관행 | 막아주는 실패 |
|---|---|
| `FROM`에 ROS 배포판 고정 | 배포판↔우분투는 1:1 (Jazzy=Noble/py3.12, Humble=Jammy/py3.10). 다른 우분투의 팀원이 패키지를 하나도 못 깜 |
| Jetson은 L4T 베이스 + NVIDIA 런타임 | 우분투·아키텍처가 맞아도 CUDA 유저스페이스가 안 맞는 이미지 (JetPack이 커널·드라이버·CUDA·TensorRT를 플래시 시점에 같이 잠금) |
| 외부 소스는 **SHA** 고정 (`.repos`, `vcs export --exact`) | 같은 Dockerfile을 일주일 간격으로 빌드한 두 사람이 다른 소스 트리 |
| `<depend>` + `rosdep check \|\| exit 1` | "될 때까지 apt" 후 태그를 안 적어 다음 클론에서만 실패 |
| underlay → overlay 순서로 source | `/opt/ros` 직접 수정 → 다음 apt 업그레이드에 조용히 복원 |
| `--symlink-install`은 "기존 파일 수정이 반영"일 뿐 | 새 launch/yaml 추가는 재빌드 전까지 install 트리에 없음 → 존재하지 않는 파일로 음성 결론 |
| `build/ install/ log/`는 git 제외, **install/은 절대 수정 금지** | symlink 반, 복사본 반 — 겉보기로 구분 불가 |
| torch/lerobot는 **별도 컨테이너** | `pip install numpy`가 rclpy가 빌드된 모듈을 교체. 24.04의 `EXTERNALLY-MANAGED`가 이것 때문인데 벤더 이미지는 `break-system-packages`로 전역 해제 |
| `network_mode: host`, `ipc: host` | 브리지 네트워크는 DDS 멀티캐스트를 안 넘김 → `ros2 topic list` 빈 채로 에러 없음. IPC 공유 없으면 공유메모리 → UDP 폴백 |
| 로컬 변경은 `docker-compose.override.yml`에 | 벤더 파일 수정 방지. 단 `-f docker-compose.yml`을 명시하면 **override 자동 병합이 꺼진다** (`container.sh start`는 override를 적용 안 함) |
| `restart: always` 끄기 | 크래시한 팔을 아무도 없을 때 재통전 |
| 좁은 `devices:` > `privileged` + `/dev:/dev` | privileged는 항상 동작해서 문제 — 하드웨어 의존성이 문서화 안 되고, 팔이 빠져도 조용함 |

### 못 하는 것 — 핵심

**디바이스를 격리하지 않는다.** 벤더 compose는 `/dev:/dev` 바인드 + `privileged: true` → 컨테이너 안팎의 `/dev/ttyACM0`은 **같은 캐릭터 디바이스, 같은 드라이버 인스턴스, 같은 반이중 버스**.
리눅스엔 시리얼 네임스페이스가 없고 tty를 두 번 여는 건 에러가 아니다. DynamixelSDK는 `O_RDWR|O_NOCTTY|O_NONBLOCK`으로 열고 **`TIOCEXCL`을 안 건다** → 두 writer 모두 성공하고 바이트가 섞인다.

> 증상은 절대 "port busy"가 아니다. **간헐적 CRC 오류와 유령 타임아웃**, `print` 하나 추가하면 사라짐.
> (팀원 PWM 실험 스택과 겹쳤을 때의 반복 세그폴트가 이것)

**udev도 격리하지 않는다.** `.rules`를 이미지에 `COPY`해도 컨테이너엔 udevd가 없어 아무것도 안 한다 — **호스트**에 설치해야 한다.
벤더 규칙 `KERNEL=="ttyACM*", DRIVERS=="ftdi_sio"`는 **구조적으로 매치 불가**(ttyACM은 `cdc_acm`). 포트 경로도 파일 네 곳에서 불일치(런치 ttyACM0/ttyACM2, xacro ttyACM1).

**GPU 드라이버 ABI도 격리하지 않는다.** RViz 창이 안 그려진 건 Mesa가 컨테이너 밖 벤더 `.so`를 반쯤 로드한 것 — ROS가 아니라 GL 경로 문제, `LIBGL_ALWAYS_SOFTWARE=1`.

**RT 권한은 줬지만 아무도 안 쓴다.** compose가 `SYS_NICE`, rtprio 99, memlock을 주는데 s6 실행 스크립트는 `chrt` 없이 `ros2 launch`만 exec. (100 Hz 비동기 USB에선 방어 가능한 선택이지만, ulimit이 보장이라고 착각하지 말 것)
