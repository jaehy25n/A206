## 3. 도구 검증 (2026-09-18, 1단계)

### 3-1. 검출기 정확도 (✅ 합성 이미지 한정)

측정: `tests/conftest.py:render_checkerboard` 가 그린 정면 9×6 합성 체커보드.
코너 참값을 알고 있으므로 오차를 직접 잰다. 원본: `tests/test_detect.py`

| 조건 | 최대 코너 오차 | 종류 |
|---|---|---|
| square 25 / 40 / 60 px, 정면·노이즈 없음 | **0.0000 px** (참값과 완전 일치) | 측정 |
| GaussianBlur σ=1.2 + 가우시안 노이즈 σ=4 | < 1.0 px (테스트 상한) | 측정 |

원근과 실제 렌즈 왜곡은 들어 있지 않다. 실촬영 정확도가 이 값이라는 뜻이 **아니다.**
"검출기 자체에는 버그가 없다"까지만 말한다.

### 3-2. OpenCV 5.0 의 반환 모양 (측정)

`cv2.findChessboardCorners` / `cornerSubPix` 가 OpenCV 5.0 에서 **(N, 2)** 를 돌려준다.
4.x 의 (N, 1, 2) 와 다르다. → `camcal.detect.find_corners` 가 항상 **(N, 1, 2) float32** 로
정규화해 반환하도록 고정했다. 이후 단계가 OpenCV 버전에 따라 갈리지 않는다.

### 3-3. 픽셀 좌표 규약 (측정 중에 드러난 함정)

합성 이미지 검증에서 모든 코너가 일정하게 **0.7071 px = √2/2** 만큼 틀렸다.
원인은 검출기가 아니라 참값 계산이었다: OpenCV 에서 정수 좌표 `u=k` 는 픽셀 k 의 **중심**이고,
픽셀 경계(= 체커보드 코너)는 `k − 0.5` 다. 참값에서 0.5 를 빼자 오차가 0 이 됐다.

> 앞으로 픽셀 좌표를 손으로 계산하는 모든 곳(리샘플링, FOV 경계, 크롭)에 같은 규약을 쓴다.
> 0.5 px 어긋남은 RMS 를 0.5 근처로 올려놓으면서도 "왜 그런지 모르겠는" 형태로 나타난다.

### 3-4. 조용히 실패하지 않는지 (✅ 실제로 실행해 확인)

## 5. 캘리브레이션 파이프라인 검증 (2026-09-18, 3단계)

실제 카메라 데이터가 아직 없으므로 **정답을 아는 합성 데이터**로만 검증했다.
`tests/synth.py` 가 알려진 K, D 로 코너를 투영하거나(왜곡 포함) 호모그래피로
이미지를 그린다(왜곡 없음).

### 5-1. K, D 복원 (✅ 합성, 정답 대비)

측정: 참값 fx=1500, fy=1494, cx=958, cy=543, k1=-0.24(배럴). 25장, 코너 노이즈 σ=0.1 px.
원본: `tests/test_calibrate_synthetic.py`

| 항목 | 결과 |
|---|---|
| fx, fy 복원 | 참값 대비 **0.5% 이내** (테스트 상한) |
| cx, cy 복원 | 20 px 이내. 초점거리보다 잘 안 잡힌다 |
| k1 부호·크기 | 배럴(음수)로 복원, 참값과 0.02 이내 |
| RMS | 주입 노이즈 0.1 px 근처 (0.05~0.20 구간) |
| 틀린 K(fx +10%)를 홀드아웃에 먹이면 | RMS 가 5배 이상 뛴다 = 홀드아웃 검사가 실제로 작동 |
| 노이즈 σ 0.1 → 2.0 | fx 표준편차가 2배 이상 증가 = 안정성 검사가 실제로 작동 |

마지막 두 줄이 핵심이다. "검사를 넣었다"와 "검사가 무언가를 잡는다"는 다르다.

### 5-2. fov_nominal 과 fov_effective 의 대소는 왜곡 부호에 따라 뒤집힌다 (측정)

fx=1527, 1920×1080, alpha=0 기준. nominal H = 64.31도.

| k1 | fov_effective H | nominal 대비 |
|---|---|---|
| −0.40 | 64.31도 | **퇴화** (아래 참조) |
| −0.25 | 71.73도 | **넓다** |
| −0.10 | 66.61도 | 넓다 |
| 0.00 | 64.31도 | 같다 |
| +0.10 | 61.94도 | 좁다 |
| +0.25 | 59.21도 | 좁다 |

배럴 렌즈(k1<0)는 가장자리를 안쪽으로 눌러 담으므로, 왜곡을 펴면 nominal 이 말하는
것보다 **더 넓은 각도를 담고 있었다**는 것이 드러난다. 직관과 반대 방향이다.

> 결론: `LUAZ fov ⊆ S10 usable fov` 게이트는 **양쪽 다 fov_effective 로** 비교해야 한다.
> nominal 로 비교하면 배럴 렌즈의 화각을 과소평가한다.

### 5-3. getOptimalNewCameraMatrix 가 조용히 포기하는 경우 (측정 → 방어)

k1 = −0.40 에서 `getOptimalNewCameraMatrix(alpha=0)` 이 **원본 K 를 그대로 돌려준다**
(fx' = fx = 1527.0 정확히 일치). 그러면 fov_effective 가 fov_nominal 과 같은 값이 되는데,
이것은 "왜곡이 없다"가 아니라 **"유효 영역을 계산하지 못했다"**는 뜻이다. 숫자만으로는
구분되지 않는다.

→ `camcal.fov.is_degenerate_k_prime()` 이 이 경우를 잡아 리포트 경고로 올린다.

### 5-4. calibrateCamera 가 같은 입력에 다른 값을 낸다 (측정 → 고정)

같은 코너 배열로 두 번 돌린 결과 (20장 합성):

```
멀티스레드(22): fx = 1497.8669530901363  /  1497.8669530890741   서로 다름
단일 스레드   : fx = 1497.8669530890738  /  1497.8669530890738   완전히 같음
시간          : 0.05s vs 0.04s (차이 없음)
```

차이는 상대오차 1e-9 로 물리적 의미가 없다. 문제는 결과 JSON 을 diff 했을 때
같은 데이터인데 숫자가 달라 보이는 것이다. → `calibrate()` 와 `holdout_rms()` 안에서만
`cv2.setNumThreads(1)` 로 감싸고 빠져나올 때 되돌린다 (촬영 도구의 실시간 검출은
스레드를 그대로 쓴다).

### 5-5. 안정성 검사가 조용히 무의미해지던 경우 (수정)

`stability(subset=15)` 인데 학습이 14장이면 `min(15, 14) = 14` 가 되어 **매 반복이
학습 전체**를 쓴다. 그러면 표준편차가 항상 정확히 0 이 나오고, 콘솔에는
`fx 1507.69 ±0.00` 으로 찍힌다. 이 0 은 "완벽하게 안정적"이 아니라 **"검사하지 않았다"**
인데 숫자로는 구분되지 않는다.

→ 부분집합을 `len(train) - 1` 이하로 강제하고(최소 3장), 요청보다 줄어들면 리포트에
경고를 올린다.

### 5-6. 리포트에 네 항목이 모두 들어가는지 (✅)

## 6. target 공간 비교 도구 검증 (2026-09-18, 4단계)

양쪽 intrinsics 가 아직 없으므로 **합성 K, D 로만** 실행했다. 아래 수치는 도구가
무엇을 계산하는지 보여주는 예시이며, **측정값이 아니다.**

### 6-1. 야코비안 계산의 자기검증 (✅)

왜곡이 없는 두 카메라(fx 1000 -> 1200)를 설계 ② 로 옮기면 면적 배율이
(1200/1000)^2 = 1.44 여야 한다. `local_stretch` 중앙값이 1% 이내로 그 값을 낸다.
항등 사상(K_src = K_dst, D 모두 0)에서는 map 이 격자 그대로, valid = 1.0,
stretch = 1.0 이다. 여기가 맞지 않으면 나머지 숫자는 전부 의미가 없다.

원본: `tests/test_remap_metrics.py`

### 6-2. stretch 는 **면적** 배율이다 (해석 주의)

야코비안 행렬식이므로 stretch 는 한 변이 아니라 넓이의 배율이다.
판정선 1.15 는 선형으로 **1.072 배**에 해당한다.

| | 면적 | 선형 |
|---|---|---|
| 판정선 | 1.15 | 1.072 |
| 초점거리 7% 차이만으로 | 1.145 | 1.070 |

즉 두 카메라의 초점거리가 7% 만 달라도 그 사실 하나로 기준에 걸린다.
리포트 표에 선형 배율을 같이 싣도록 했다. 판정선을 어느 쪽에 걸지는 실측값을 보고 정한다.

### 6-3. 매핑 방향 (설계 ②/③ 의 구현 차이)

| 설계 | K_target | D_target | 함수 |
|---|---|---|---|
| ③ 가상 카메라 | LUAZ 의 K' (alpha=0) | **0** | `build_map_to_pinhole` |
| ② LUAZ 원본 | LUAZ 의 K | **LUAZ 의 D** | `build_map_to_distorted` |

`build_map_to_distorted` 에 `D_dst = 0` 을 넣으면 두 함수의 결과가 **같아진다**
(테스트로 고정). 이것이 README 의 경고 "`K_target = K_luaz` 로 둔다고 ② 가 되는 것이
아니다. `D_target` 이 0 이면 ③ 이다" 를 코드로 확인한 것이다.

### 6-4. matplotlib 이 한글을 두부로 그린다 (측정 → 수정)

히트맵 제목에 한글을 넣었더니 `UserWarning: Glyph 44032 missing from font(s)
DejaVu Sans` 가 줄줄이 나오고, **PNG 는 그대로 만들어졌다.** 글자가 전부 네모로
찍힌 그림이 조용히 나온다 (경고는 로그에 묻힌다).

`cv2.putText` 의 한글 미지원과 같은 종류의 문제다. → 그림에 들어가는 문자열은
ASCII 전용(`ascii_label`)으로 분리하고, 히트맵 렌더 중 `missing from font` 경고가
하나라도 나오면 실패하는 테스트를 추가했다.

### 6-5. 합성 실행 예시 (⚠️ 측정값 아님)

입력: s10 fx=1380 k1=-0.11 / luaz fx=1527 k1=-0.24 (둘 다 임의의 합성값)

```
  게이트  luaz fov_effective ⊆ s10 fov_effective ? 통과 (여유 H +2.55 / V +3.22 도)
  설계 ③  s10  -> 가상 카메라: valid 100.00% · stretch 95p 1.276 · 최대 1.328
  설계 ③  luaz -> 가상 카메라: valid  99.97% · stretch 95p 1.323 · 최대 1.459
  설계 ②  s10  -> luaz 원본  : valid 100.00% · stretch 95p 1.212 · 최대 1.221
  설계 ②  luaz               : 변환 없음
```

설계 ② 의 최대 stretch 1.2215 는 초점거리 비의 제곱 (1527/1380)^2 = 1.2244 와 맞는다.
계산이 맞다는 신호이지 LUAZ 의 성질이 아니다.
